# sysmon

Portable-утилита для диагностики того, что реально грузит Windows-машину (CPU, память, диск по процессам), без установки чего-либо и без прав администратора. Родилась из задачи "ускорить рабочий ноутбук на Windows 11, не имея админских прав" — сначала измеряем факты, потом решаем, что чинить.

Состоит из:

- **`SystemMonitor`** — сэмплер, пишет CSV с нагрузкой по процессам.

## Требования

- JDK 21 (используется как toolchain; сборка возможна и без него — см. запуск без Gradle).
- Windows 10/11. Права администратора не нужны нигде: `SystemMonitor` только читает системные счётчики.

## Быстрый запуск без сборки

Java 11+ умеет запускать `.java`-файл напрямую, без явной компиляции (JEP 330) — этого достаточно, чтобы ничего не собирать и не устанавливать:

```bash
java SystemMonitor.java --interval=10 --out=samples/day1.csv
```

Единственное ограничение: `SystemMonitor` тянет зависимость OSHI (JNA), поэтому для него такой запуск потребует OSHI-jar в classpath (`java -cp oshi-core-6.6.5.jar;jna-....jar SystemMonitor.java ...`). Проще — собрать fat-jar через Gradle один раз (см. ниже) и дальше носить с собой только его.

## Сборка portable jar

```bash
./gradlew shadowJar
```

Результат — `build/libs/sysmon.jar`, один файл со всеми зависимостями внутри. Копируется на любую машину и запускается:

```bash
java -jar sysmon.jar --interval=10 --out=samples/day1.csv
```

## SystemMonitor — как работает

Раз в `--interval` секунд (по умолчанию 10) опрашивает список процессов через OSHI и дописывает строки в CSV. CPU считается как **дельта между двумя последовательными снимками** одного и того же PID (`getProcessCpuLoadBetweenTicks`), а не как накопленное с момента старта значение — это важно, иначе цифры будут расти монотонно и станут бесполезны для анализа "здесь и сейчас".

Формат CSV:

| Колонка         | Смысл                          | Природа значения                                    |
| --------------- | ------------------------------ | --------------------------------------------------- |
| `timestamp`     | момент замера, ISO-8601        | —                                                   |
| `pid`           | идентификатор процесса         | —                                                   |
| `name`          | имя процесса                   | —                                                   |
| `cpu_percent`   | загрузка CPU с прошлого замера | **дельта** — можно усреднять по строкам             |
| `resident_mb`   | резидентная память (RSS)       | мгновенный снимок — можно усреднять                 |
| `disk_read_kb`  | прочитано с диска              | **накопительный счётчик** с момента старта процесса |
| `disk_write_kb` | записано на диск               | **накопительный счётчик** с момента старта процесса |

Процессы с `resident_mb < 20` и `cpu_percent < 1.0` в конкретном замере пропускаются — это просто шумовой фон, не несущий сигнала.

## Особенности

Для `PID 0` (System Idle Process) и `vmmemWSL` (VM-хост Hyper-V/WSL2) дельта-расчёт CPU иногда даёт `avg > max` в агрегатах — это физически невозможно для корректных данных и указывает на то, что учёт тиков для этих процессов через API Windows работает нестандартно. При анализе такие строки стоит исключать (`WHERE pid <> 0`) и не доверять их CPU-цифрам.

Также замечено, что `resident_mb` для некоторых процессов (в частности, для `idea64` — при том что IntelliJ обычно потребляет сотни МБ – единицы ГБ) может выдавать неправдоподобно низкие значения. Причина пока не подтверждена (кандидаты: ограничение доступа к дескриптору процесса на уровне ОС без admin, либо баг в самой утилите) — перед выводами по памяти конкретного процесса сверяйтесь с Task Manager в реальном времени.

## Анализ CSV через SQL

Файл открывается любым инструментом, умеющим гонять SQL по CSV (например, плагин **CSV Query** для Notepad++, который парсит CSV в SQLite-таблицу в памяти и обращается к ней через ключевое слово `this`). Имейте ввиду в Notepad++ SQL надо писать в одну строку.

## Топ по CPU

```
sqlSELECT name,
       ROUND(AVG(cpu_percent), 1) AS avg_cpu,
       ROUND(MAX(cpu_percent), 1) AS max_cpu,
       COUNT(*) AS samples
FROM this
WHERE pid <> 0            -- исключаем System Idle Process, там ломается дельта
GROUP BY name
ORDER BY avg_cpu DESC
LIMIT 20;
```

## Топ по памяти

```
sqlSELECT name,
       ROUND(AVG(resident_mb), 0) AS avg_mem_mb,
       ROUND(MAX(resident_mb), 0) AS max_mem_mb
FROM this
GROUP BY name
ORDER BY avg_mem_mb DESC
LIMIT 20;
```

## Топ по диску

`disk_read_kb`/`disk_write_kb` — накопительные счётчики, поэтому усреднять их по строкам нельзя (получите завышенную в разы цифру). Берём максимум на конкретный `pid`, затем суммируем по имени (на случай, если процесс за день перезапускался под разными PID):

```
sqlSELECT name,
       SUM(max_read)  AS total_read_kb,
       SUM(max_write) AS total_write_kb
FROM (
    SELECT pid, name,
           MAX(disk_read_kb)  AS max_read,
           MAX(disk_write_kb) AS max_write
    FROM this
    GROUP BY pid, name
) t
GROUP BY name
ORDER BY (total_read_kb + total_write_kb) DESC
LIMIT 20;
```

## Экспорт с явным разделителем

Если результат нужно скопировать текстом (например, чтобы обсудить с кем-то или вставить в другой инструмент) — конкатенируйте поля с явным разделителем, иначе числа сольются без пробелов и станут не читаемы:

```
sqlSELECT name || ' | ' || total_read_kb || ' | ' || total_write_kb AS row_text
FROM (...) -- см. запрос выше
ORDER BY total_read_kb + total_write_kb DESC
LIMIT 20;
```
